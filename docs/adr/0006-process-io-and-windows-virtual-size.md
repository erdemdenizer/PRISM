# 0006. Process metric semantics: process I/O, and the Windows virtual size

- Status: Accepted
- Date: 2026-10-05

## Context

Verifying the process snapshot on Windows showed that two values were not what their
names said.

**Read and write rates.** The specification asked for a "disk read and write rate" per
process. The only cheap per-process counters Windows has are the I/O counters of the
Process performance object, and Microsoft documents them as counting "all I/O activity
generated by the process to include file, network, and device I/Os". A browser that
downloads a file would show as disk activity. Linux counts something narrower:
`read_bytes` and `write_bytes` of `/proc/<pid>/io` are what the process caused to be
fetched from or sent to the storage layer. On macOS OSHI reads the fields
`ri_diskio_bytesread` and `ri_diskio_byteswritten` of `proc_pid_rusage`; their names say
disk I/O, and Apple does not document them.

**Virtual size.** OSHI's Windows process listing returns `PagefileUsage` of
`WTS_PROCESS_INFO_EX` under that name: committed memory, in a 32-bit field. For one JVM
OSHI gave 1441 MiB where `Win32_Process.VirtualSize` gave 13 731 MiB. The first
implementation therefore reported no virtual size on Windows. Windows does provide the
value; the question was at what cost. Measured on the development machine, about 392
processes, one read per 2-second cycle, 60 cycles, machine under load (the listing
itself took 60 to 68 ms in the median):

| Source, one read for all processes | Median | Mean | Worst |
|---|---|---|---|
| `Win32_Process` (ProcessId, CreationDate, VirtualSize) through WMI | 620 ms | 637 ms | 928 ms |
| "Virtual Bytes" of the Process object through PDH (30 cycles) | 128 ms | 133 ms | 258 ms |
| "Virtual Bytes" of the Process object through `HKEY_PERFORMANCE_DATA` | 12.6 ms | 12.5 ms | 18.1 ms |

The WMI query also raised the CPU use of the measuring JVM from 6.6% to 33.9% of one
logical processor. The three sources return the same number: Microsoft documents
`Win32_Process.VirtualSize` as "consistent with what you see in Perfmon.exe". In one
comparison of 393 processes the counter and the WMI property were equal for 385; seven
had changed by less than 5% between the two reads, and the comparison itself misread the
idle process. Through Prism, seven of the eight oldest processes had the value of the
WMI property to the byte; the eighth changes from read to read.

## Decision

1. **The per-process rates are process I/O, and are named so everywhere**: PROC-1, the
   Processes column ("I/O", never "Disk"), `ProcessReading.bytesRead` / `bytesWritten`,
   `ProcessSnapshot.ioReadBytesPerSecond` / `ioWriteBytesPerSecond`. The name is true on
   Windows and stays true for the narrower counters of Linux and macOS. What each system
   counts is documented on the reading. Disk rates exist for the whole system only
   (MON-4) and are unchanged.
2. **The Windows virtual size is the "Virtual Bytes" counter of the Process performance
   object**, read through `HKEY_PERFORMANCE_DATA` once per listing for all processes,
   behind `ProcessVirtualSizeSource` in `platform`, implemented in `platform.windows`.
3. **A value is given to a process only when PID and creation time both match** the
   identity in the listing. The counter block holds the creation time; it is the value
   OSHI derives the start time from, so the two are equal to the millisecond. A process
   that the second read does not hold has no virtual size.
4. **The read is optional.** If it fails with a `RuntimeException`, the listing is
   delivered without virtual sizes and Prism logs the failure once per kind; OSHI's
   reader may log on every failed read. An `Error` is not caught.
5. **The Windows process state stays absent.** OSHI's value is a default, not a reading.
   `Win32_Process.ExecutionState` is not filled by Windows (empty for all 393 processes
   on the development machine). Thread enumeration and OSHI's suspended-state scan stay
   off. A later requirement has to bring a mechanism that is reliable and affordable.

## Alternatives considered

- **Keep the name "disk" and document the difference.** The wrong name would reach the
  column header, where no documentation is read.
- **A true per-process disk counter on Windows.** No documented, cheap counter is known.
  Tracing disk I/O with ETW is a subsystem of its own and out of scope.
- **`Win32_Process.VirtualSize` on every cycle.** The documented class for the value,
  and the identity match works (23 415 of 23 455 readings; the 40 others had exited).
  At 620 ms it is ten times the listing and 31% of the interval.
- **`Win32_Process` every 10 to 30 seconds.** Affordable, but the value is then up to
  that old and needs an age rule; the counter makes it unnecessary.
- **PDH**, the interface Microsoft recommends over the registry functions. Ten times
  the cost of the registry read for the same data.
- **Leave the virtual size absent.** Not justified once a 13 ms source exists.

## Consequences

- A process listing on Windows reads the Process performance object twice: once inside
  OSHI and once for the virtual sizes. Measured in pairs over 100 cycles, the second
  read adds 13.9 ms in the median to a listing of 57.2 ms.
- A process that exits between the two reads has no virtual size in that snapshot (7 of
  39 256 readings in the paired measurement).
- The read is inside the time a listing takes, which the process sampler dates at its
  midpoint, while the processor counters are taken in the first part. The midpoint is
  late by half the read, 4 to 7 ms; that is the same in every cycle and cancels between
  two readings. What remains is the difference between two reads, a few milliseconds in
  2000. Measured after the change, process CPU stayed within 0.6 points of the system's
  own figure, as before. A read that stalled for a second would move one interval by
  half a second and the next one back; the registry read has no timeout, as OSHI's own
  listing has none.
- `WindowsProcessVirtualSizes` uses OSHI's reader
  `oshi.driver.windows.registry.HkeyPerformanceDataUtilJNA`. The package is not exported
  by OSHI's module descriptor: the class is reachable only while Prism runs on the class
  path, and an OSHI upgrade must re-check it. Reading `HKEY_PERFORMANCE_DATA` directly
  through `jna-platform` is the replacement if either changes.
- On the module path the call would fail with a `LinkageError`. That is an `Error`, so
  it is not caught and ends process monitoring: for that one failure the read is not
  optional. It cannot occur with the class path and the pinned OSHI of today. Packaging
  (milestone 13) must either keep the class path or replace the reader first. Catching
  `LinkageError` at this one call was considered and left to a decision, because the
  project rule is that an `Error` is never caught.
- That the raw "Elapsed Time" value of the Process object is a FILETIME is observed and
  relied on by OSHI, not documented; documented is only that it is the start time on
  the object's own clock. That a standard user may read the performance data without
  elevation is observed as well.
- Microsoft recommends PDH over the registry functions for general use. OSHI's own
  process listing already depends on the registry interface, so this adds no new kind of
  dependency; where performance counters are disabled, the virtual size is absent.
- The identity match relies on OSHI and Prism cutting the same creation time to
  milliseconds the same way. If OSHI changed its conversion, no identity would match and
  every virtual size would be absent: wrong values cannot result. The probe fails when
  the probe's own process has no virtual size.
- The process I/O rates of Windows and of Linux or macOS are not comparable in size. The
  UI must not suggest that they are disk rates on any system.
- Nothing here has been run on Linux or macOS.
